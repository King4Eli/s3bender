# Auth and signing

s3bender uses a small custom HMAC scheme, deliberately simpler than AWS SigV4. It is **not**
AWS-compatible - you cannot point the AWS CLI or an S3 SDK at it. This is a design choice, not a
gap: per-bucket credentials and a minimal request surface don't need SigV4's complexity. This spec
is exact and language-independent so it can be reimplemented identically anywhere.

## Two credential types

| credential            | scope                          | who has it              |
|------------------------|---------------------------------|--------------------------|
| Admin API key          | every `/admin/*` route          | operator only            |
| Bucket access/secret key | that bucket's `/buckets/{name}/*` routes | whoever provisioned the bucket |

The admin key is a plain shared-secret header check (`X-Admin-Api-Key`), constant-time compared.
Everything below is about the bucket key pair.

## String-to-sign

Two variants, chosen by which auth form is used. Both use `\n` (single LF, no CR) as separator,
and both compute an HMAC-SHA256 over UTF-8 bytes, hex-encoded (lowercase) as the signature.

**Header auth** (control-plane and data-plane requests alike):

```
StringToSign = HTTP_METHOD + "\n" + PATH + "\n" + TIMESTAMP
Signature    = hex(HMAC_SHA256(secretKey, StringToSign))
```

**Presigned URL** (query-string auth, GET/PUT/HEAD only):

```
StringToSign = HTTP_METHOD + "\n" + PATH + "\n" + EXPIRES
Signature    = hex(HMAC_SHA256(secretKey, StringToSign))
```

Where:

- `HTTP_METHOD` - uppercase, e.g. `GET`, `PUT`, `POST`.
- `PATH` - the request's URL path only (no scheme/host/query), **percent-decoded** exactly once
  (so `%20` in a key becomes a literal space before signing). No query string is included in
  either variant, so query parameters (other than the auth params themselves) are not covered by
  the signature - avoid designs that rely on other query params for authorization decisions.
- `TIMESTAMP` / `EXPIRES` - decimal Unix epoch **seconds** (not millis), as a plain base-10 string
  with no leading zeros.
- **The request body is intentionally excluded from the signature.** This keeps large uploads
  streamable without buffering the whole body to compute a hash. It means the signature proves
  "this caller, with this secret, authorized this method+path at this time" but not "this exact
  byte content" - equivalent to AWS's `UNSIGNED-PAYLOAD` mode for presigned uploads. Because of
  this, s3bender must always run behind TLS in any real deployment (see deployment.md) - signing
  the transport, not the payload, is only safe if the transport itself is trusted.

## Header auth

```
Authorization: S3BENDER-HMAC-SHA256 AccessKey=<accessKey>,Timestamp=<epochSeconds>,Signature=<hex>
```

No spaces around the `=`, comma-separated, no trailing content. Server-side validation:

1. Parse `AccessKey`, `Timestamp`, `Signature` out of the header. Malformed header → `401`.
2. Look up the bucket by `AccessKey`. Not found, or the bucket named in the request path doesn't
   match the bucket that owns this access key → `401`.
3. Reject if `|now - Timestamp| > clockSkewSeconds` (default 900s / 15 min, configurable via
   `S3BENDER_CLOCK_SKEW_SECONDS`) → `403`. This bounds how long a captured header is replayable.
4. Recompute the signature server-side with the bucket's decrypted secret key and the same
   `StringToSign` layout above; compare to the provided signature using a **constant-time**
   comparison → mismatch is `403`.

## Presigned URLs

Generated by an authenticated (header-auth) call to `POST /buckets/{bucket}/presign`:

```json
{ "key": "docs/report.pdf", "method": "GET", "expiresInSeconds": 3600 }
```

Server computes `Expires = now + expiresInSeconds` (rejecting anything past
`S3BENDER_MAX_PRESIGN_EXPIRY_SECONDS`, default 7 days), signs
`METHOD "\n" PATH "\n" Expires` with the bucket secret, and returns:

```
{scheme}://{host}/buckets/{bucket}/objects/{key}?AccessKey={accessKey}&Expires={epoch}&Signature={hex}
```

To validate an incoming presigned request:

1. Require `AccessKey`, `Expires`, `Signature` all present as query params, and method is
   GET, PUT, or HEAD (presigned URLs are not accepted for DELETE, LIST, or admin operations - those
   always require header auth).
2. Reject if `now > Expires` → `403` (no clock-skew allowance here; `Expires` is already an
   absolute deadline the client chose).
3. Recompute and constant-time-compare the signature exactly as above, using `Expires` in place of
   `Timestamp`.

## What a reimplementation must preserve

- The exact string-to-sign byte layout (method, single `\n`, decoded path, single `\n`,
  timestamp/expires as decimal seconds) - change this and old signatures/URLs stop validating.
- HMAC-SHA256, hex-encoded, lowercase.
- Constant-time signature comparison (never `==`/`.equals` on the raw signature strings).
- Body excluded from the signature.
- Presigned auth restricted to GET/PUT/HEAD.
- Access-key-to-bucket binding check (a valid signature for the wrong bucket path must still fail).

## What's safe to change

- Clock-skew and max-presign-expiry values (they're config, not protocol).
- The admin-key transport (header vs. some other out-of-band mechanism), since it never touches
  object signing.
- Access/secret key generation format (length, charset) - only the *values* need to be opaque
  random strings, not their encoding.
